# Lootwright

A WoW Forever addon. The player types an item name and sees which mobs drop it, their zone, level range, rank and drop rate. Later: mark those mobs on the map.

Read `ROADMAP.md` for the full plan. This file is the short version plus the facts learned so far.

**Name:** renamed from ItemFinder to **Lootwright** in Nov 2026 ("ItemFinder" is taken on CurseForge by ItemFinder Classic, and a Wildstar addon). Addon folders and TOCs: `Lootwright`, `Lootwright_Data`, `Lootwright_Professions`; globals `LootwrightDB` (saved variables), `LootwrightNS` (shared namespace); slash `/if` and `/lootwright` (not `/itemfinder`, which ItemFinder Classic uses). The repo folder on disk is still `I:\VibeStuff\Wow addons\ItemFinder`; only the AddOns junctions carry the new names. Old commits say ItemFinder.

## Versions and changelog

Claude decides when to bump and says so. Versions are `major.minor.patch`; under 1.0 the addon is an "early version". Since 0.10.0 files go up as CurseForge **Release** type (0.9.0 was a Beta file; Beta files are hidden in the CurseForge app by default), so don't call it "a beta" in player-facing text: say "early version". WoW Forever itself is not in beta either, so never say it is.

- **Patch** (0.10.0 -> 0.10.1): bug fixes, a data rebuild, text or colour tweaks. Nothing new to learn for the player.
- **Minor** (0.10.x -> 0.11.0): a new feature, command or option, a new data source, or a change to what's saved (`LootwrightDB` layout).
- **Major** (1.0.0): no longer an early version. Only when the user says so.
- **When:** one bump per release, not per commit. The first change after a release that makes the next version a minor (or patch) one bumps it right away, so the repo always says what the next upload will be. A later bigger change raises it again (patch -> minor) before release.
- **Every bump:** `python -I tools/release.py bump patch|minor|<x.y.z>` sets `## Version` in all three TOCs and `VERSION` in `Core.lua`, and opens (or renumbers) the "not released yet" section at the top of `CHANGELOG.md`. Then update `docs/changelog.html` by hand and republish it.
- **Build a release:** `python -I tools/release.py` runs `build_data.py` and `package.py`, checks the versions match and that `CHANGELOG.md` has a section for this version, and prints that section to paste into CurseForge. After uploading: `python -I tools/release.py released` dates the section.
- **Every user-visible change:** add a line to the top `CHANGELOG.md` section in the same commit, in the player's words (New / Changed / Fixed, plus "For developers"). Then republish the changelog page: source `docs/changelog.html`, published at the pinned changelog artifact (URL below). Keep both in step.
